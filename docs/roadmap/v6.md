### Goal and scope

Expose uptime and latency analytics through the API and build the first useful
Next.js dashboard. Add live updates only after evaluating polling, Server-Sent
Events, and WebSockets against the actual product requirements.

### Real-time decision checkpoint

Do not preselect WebSockets. Before implementing live updates, document:

- whether communication is server-to-client only or bidirectional;
- acceptable update delay and connection volume;
- authentication and token-refresh behavior;
- reconnect, missed-event, and authoritative-refetch behavior;
- proxy/deployment support and operational complexity.

Select the simplest transport that satisfies those requirements. Polling, SSE,
and WebSockets are all valid candidates until this checkpoint is complete.

### Incidents page (sequenced — implement after the other V6 features above)

Build the incidents page **last**, once the core dashboard, aggregation, and
pagination work is done. It is part of V6 but deliberately deferred so the read
path and analytics land first. Two slices, in order:

1. **Incidents read path → frontend.** List + summary stats (MTTR, total, active
   count, plus one more card) queries → services → controllers, then wire to the
   Next.js page. Both endpoints take an optional `monitorId` query param
   (backend filtering — the stats are aggregates and cannot be filtered
   client-side); cards scope to the active filter. List/stats return `200` with
   an empty array / zeroed stats on no rows (do **not** reuse the single-incident
   `404`-on-empty pattern). Ownership via join on `monitor.user_id`. The detail
   read path (`getSingleIncidentsDetailsById`) already exists as the pattern.
2. **Manual incident updates / status timeline.** New `incident_updates` table
   (`id`, `incident_id`, `status`, `message`, `created_at`) plus a post-update
   form. Render a merged timeline: auto **Detected**/**Resolved** markers (from
   `incidents.started_at`/`resolved_at`) interleaved with human
   Investigating/Monitoring notes. Resolution stays **worker-driven** — the form
   is commentary only and never changes the incident lifecycle.

Real-time note: the live `incident_created` / `incident_resolved` SSE events
(producer in `stateMachine.worker.ts`, plus their frontend consumer) ship with
this incidents slice, not the core SSE work. The core SSE transport delivers
`check_result` events only; the dashboard's live UP/DOWN status is already
covered by those.

Data note: the mocked UI's per-incident `title` and `description` are not stored
on `incidents`. Synthesize `title` from `url_name`; the `description` raw
material (`status_code`, `error_message`) lives in `url_checks` and can be joined
at read time, or denormalized onto `incidents` later.

### Cleanup (post-V6 — after the features above)

- **Standardize 401 response strings (DONE 2026-07-10).** Backend 401 responses
  now use `{ message: "Unauthenticated" }`; the scan is clear for the old
  `"UnAuthorized"`, `"Unauthorized"`, and `"Token is expired"` strings.

- **Backend folder/module refactor (PARTIAL 2026-07-10).** Feature-first backend
  folders are in place (`modules/*`, `shared/*`, `sse/*`, `redis/*`, `workers/*`,
  `scheduler/*`). Import wiring is fixed, app typecheck passes, migration
  typecheck passes, and backend build with declarations passes. Migrations moved
  out of `src` to `apps/backend/migrations`, with separate
  `tsconfig.migrations.json` so migration tooling does not block the app
  compiler. Module route aggregators now expose noun-style API paths, and stale
  pre-refactor route files were removed. Remaining work is the convention sweep
  below, not compile wiring.

- **Backend alignment pass (agreed 2026-07-04).** New folder structure plus
  one convention sweep across ALL endpoints — many predate current patterns.
  Checklist accumulated from V6 reviews (subsumes the 401 item above):
  1. Errors (DONE 2026-07-10): controllers and auth middleware do not write
     failure responses directly; error responses are emitted by the shared error
     middleware.
  2. Zod (DONE 2026-07-10): controllers use parsed values, and `ZodError`
     reaches the shared error middleware as `400 VALIDATION_ERROR` with
     field-level `{ path: message }` details.
  3. One success envelope (DONE 2026-07-10): single-resource and action
     responses use `{ data }`; lists use `{ data, pagination }`; existing
     no-body actions use `204 No Content`.
  4. Routes (DONE 2026-07-10): nouns not verbs (`POST /:incidentId/updates`,
     not `/:id/add`); the HTTP method is the verb; param names match what
     controllers read.
  5. One name per concept (DONE 2026-07-10 for incident updates): the API uses
     `type` for the `incident_updates` lifecycle type. The frontend may still
     call its form field `status`, but it sends `type` to the backend.

- **SSE endpoint env var (DONE 2026-07-06).** Renamed
  `NEXT_BACKEND_SSE_ENDPOINT` → `NEXT_PUBLIC_SSE_ENDPOINT` across all frontend
  SSE hooks, `sse/sse-events.ts`, the connection-status provider, and
  `.env.local`. Without the `NEXT_PUBLIC_` prefix the value was `undefined` in
  the browser and every EventSource silently fell back to
  `http://localhost:5000/sse/events`. **Deploy caveat:** `NEXT_PUBLIC_*` vars
  are inlined at *build* time, so production must set
  `NEXT_PUBLIC_SSE_ENDPOINT` to the deployed backend's `/sse/events` URL and
  **rebuild** the frontend — it cannot be flipped on a running container.

#### Mental model: when to use `useWatch` (react-hook-form)

RHF keeps form values in a "notebook" outside React state, so writing a value
re-renders nothing. For each value, ask: **"does a visible pixel depend on
this while the form is open?"**

- User types into a native input → `register` only; the browser paints the
  text itself, no re-render needed.
- A visible pixel depends on it (button highlight, char counter, show/hide a
  section, preview text, disabled state) → `useWatch`, the "bell" that makes
  React redraw when the notebook changes.
- Needed only at one moment (submit or click handler) → `handleSubmit`'s
  `data` or `getValues()`; reading once needs no subscription.
- `errors` / `isValid` → come from `formState`, which is already reactive —
  never watched.

Failure mode without it: logic keeps working but the screen freezes — the
highlight doesn't move, the counter sticks at 0/500. No crash, just a UI that
lies. (Reference implementation: the incident-update modal.)
