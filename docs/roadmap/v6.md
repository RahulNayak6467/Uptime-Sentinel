### Goal and scope

Expose uptime and latency analytics through the API and build the first useful
Next.js dashboard. Add live updates only after evaluating polling, Server-Sent
Events, and WebSockets against the actual product requirements.

### Core features

- [x] Dashboard summary with UP/DOWN counts and overall uptime.
- [x] Per-monitor metrics for `24h`, `7d`, and `30d` ranges.
- [x] Paginated monitor tables on the overview and monitors pages.
- [ ] Paginated incident history (sequenced with the incidents page below).
- [x] Response-time series rendered with **Apache ECharts** through
  `echarts-for-react`.
- [x] Next.js dashboard, monitor list, and monitor-detail pages using TanStack
  Query, Tailwind CSS, and shadcn/ui.
- [ ] Evaluate polling vs SSE vs WebSockets before implementation.
- [ ] Implement the selected live-update transport, including worker-to-API
  event delivery through Redis Pub/Sub if cross-process broadcasting is needed.

### Real-time decision checkpoint

Do not preselect WebSockets. Before implementing live updates, document:

- whether communication is server-to-client only or bidirectional;
- acceptable update delay and connection volume;
- authentication and token-refresh behavior;
- reconnect, missed-event, and authoritative-refetch behavior;
- proxy/deployment support and operational complexity.

Select the simplest transport that satisfies those requirements. Polling, SSE,
and WebSockets are all valid candidates until this checkpoint is complete.

### Incidents page (sequenced — implement after the other V6 features above)

Build the incidents page **last**, once the core dashboard, aggregation, and
pagination work is done. It is part of V6 but deliberately deferred so the read
path and analytics land first. Two slices, in order:

1. **Incidents read path → frontend.** List + summary stats (MTTR, total, active
   count, plus one more card) queries → services → controllers, then wire to the
   Next.js page. Both endpoints take an optional `monitorId` query param
   (backend filtering — the stats are aggregates and cannot be filtered
   client-side); cards scope to the active filter. List/stats return `200` with
   an empty array / zeroed stats on no rows (do **not** reuse the single-incident
   `404`-on-empty pattern). Ownership via join on `monitor.user_id`. The detail
   read path (`getSingleIncidentsDetailsById`) already exists as the pattern.
2. **Manual incident updates / status timeline.** New `incident_updates` table
   (`id`, `incident_id`, `status`, `message`, `created_at`) plus a post-update
   form. Render a merged timeline: auto **Detected**/**Resolved** markers (from
   `incidents.started_at`/`resolved_at`) interleaved with human
   Investigating/Monitoring notes. Resolution stays **worker-driven** — the form
   is commentary only and never changes the incident lifecycle.

Real-time note: the live `incident_created` / `incident_resolved` SSE events
(producer in `stateMachine.worker.ts`, plus their frontend consumer) ship with
this incidents slice, not the core SSE work. The core SSE transport delivers
`check_result` events only; the dashboard's live UP/DOWN status is already
covered by those.

Data note: the mocked UI's per-incident `title` and `description` are not stored
on `incidents`. Synthesize `title` from `url_name`; the `description` raw
material (`status_code`, `error_message`) lives in `url_checks` and can be joined
at read time, or denormalized onto `incidents` later.

### Cleanup (post-V6 — after the features above)

- **Standardize 401 response strings.** Controllers now return
  `{ message: "Unauthenticated" }` consistently, but `auth.middleware.ts` still
  emits mixed strings (`"UnAuthorized"`, `"Unauthorized"`, `"Token is expired"`)
  and `authRefresh.services.ts` returns leftover debug strings
  (`"Unauthorized1"`, `"Unauthorized2"`). The middleware runs before controllers,
  so most real 401s come from there — align all 401 bodies on one key
  (`message`) and one casing so the frontend can match a single contract.
