# V4 — Queue and Worker

> Part of the [StatusForge roadmap](../../ROADMAP.md). See the index for the full
> version map, current state, and the deferred-work register.

**Status:** Not started

### Goal and scope

Move monitor execution out of the API process. The scheduler and manual-check
route become producers; a separate BullMQ worker becomes the consumer.

### Core features

- [ ] Redis and BullMQ check queue.
- [ ] Scheduler enqueues due checks instead of executing them.
- [ ] Manual check enqueues a job and returns `202 Accepted`.
- [ ] Separate worker executes checks, persists results, and updates snapshots.
- [ ] Configurable worker concurrency, retries with exponential backoff, failed
  job logging, and dead-letter handling.
- [ ] Redis-backed access-token blacklist checked by auth middleware.

### Supporting work

- [ ] Stable job IDs/idempotency and concurrent-check prevention.
- [ ] Worker health check and graceful shutdown.
- [ ] `REDIS_URL` validation and Bull Board for development visibility.
- [ ] Introduce schema migrations and convert existing ad-hoc table creation.
- [ ] Use a basic Redis Docker container for local development.

### Concepts learned

Producer/consumer architecture, Redis infrastructure, BullMQ lifecycle,
backoff, dead-letter queues, `202 Accepted`, idempotency, distributed locking,
token revocation, database migrations, and multi-process applications.

### Out of scope

Incident state machines, alerts, analytics, real-time browser updates, and
multi-region workers.
